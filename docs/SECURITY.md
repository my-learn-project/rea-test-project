# 授权卡密 Demo 安全说明

本项目是用于学习和验证工作流的离线授权 Demo。目标是演示“管理端签发、Qt 客户端提交、Rust 校验”的完整流程，并使普通的卡密篡改被拒绝。它不代表经过独立审计的商业授权平台，也不承诺“顶尖安全”“无法破解”或“永久防破解”。

## 信任边界

| 组件 | 应持有的数据 | 分发范围 |
| --- | --- | --- |
| 正式发卡工具 | 加密的 Ed25519 签名私钥、解密口令 | 仅管理端，和用户客户端分开发行 |
| Rust 校验静态库 | 构建时固定的验签公钥、授权协议代码 | 静态链接进 Qt 主程序 |
| Qt 界面 | 输入的卡密、设备标识、校验结果 | 客户端 |
| 受保护的授权策略函数 | 已验证状态位、签发/到期/当前时间，不持有秘密 | 作为 object 链接进 Qt 主程序 |
| `license-client` CLI | 与静态库同源的诊断接口 | 诊断、签发辅助与集成测试；GUI 不调用 |
| `demo/keys` 公开测试身份 | 加密测试私钥、配套公钥、明文测试口令 | 源码测试材料，任何人可使用；不属于正式身份 |
| 授权卡密 | 已签名的授权内容 | 授权用户；按凭据保护 |

公钥允许公开。正式私钥一旦泄露，攻击者可以生成有效签名；为程序加壳或隐藏公钥无法补救私钥泄露。正式发行私钥及其口令不得进入源码、客户端安装包、日志、工单或聊天消息。

本仓库刻意公开 `demo/keys/demo.private.json`、`demo.public.hex` 与 `demo.passphrase.txt`，供克隆后跨平台测试。测试私钥虽然保留加密文件格式，明文口令也已公开，任何人都能解密并签发被该 demo 公钥信任的测试卡。因此这套身份没有签发者保密边界，不能用于正式授权。源码测试材料不会自动混入客户端发行包，Windows 本机 `.local` 与 DPAPI 文件仍不提交。

`prepare-demo.py` 只在构建公钥缺失时复制公开 demo 公钥；已有不同公钥会被拒绝覆盖。`issue-demo.py` 默认使用公开测试身份，为指定 `.app` 读取到的本机身份签卡并写入 `.local/demo-card.txt`，不向标准输出打印卡密。它们不替换或修改 Windows 当前 `.local` 身份。CI 默认信任 demo 公钥，仓库公钥变量可覆盖最终构建；公开 demo 验证与一次性测试身份验证均属于测试流程，不能据此宣称发行私钥受到保护。

## 安全机制与作用

- 使用 Ed25519 非对称签名，使客户端不需要获得发卡私钥。校验端应对签名的原始字节验证，拒绝错误格式、未知协议版本、过长输入、错误产品、过期时间和不匹配的设备绑定。
- 公钥应固定在发行版构建中；把任意本地公钥文件当作可信根会使攻击者可以自签授权。替换公钥需要重建客户端，同时制定密钥轮换与旧版本退出方案。
- 使用 `ed25519-dalek` 的 `verify_strict()`。该接口执行严格验签，包括额外的弱公钥和签名可塑性检查；这不替代授权字段的业务校验。[ed25519-dalek 官方接口说明](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict)
- 私钥文件应通过口令派生密钥及认证加密保护。强随机盐、随机 nonce 与内存清零只能降低部分风险，不能保护已被恶意软件或管理员完全控制的发卡主机。
- 卡密经签名保证真实性与完整性，签名不隐藏其内容。不要在授权内容中写入密码、身份证号或无需客户端知道的个人信息。

上述条目描述设计要求；实际命令、参数和构建步骤以项目 README 为准。测试覆盖范围和本次验证结果应以实际测试记录为准，不能把文档作为某项测试已经执行的证据。

## Demo 授权协议

令牌格式为 `L1.<payload>.<signature>`，后两段使用不带 padding 的 Base64URL。签名消息是固定域 `card-demo/license/v1\0` 加上原始 JSON payload 字节；先验签，再解释字段，避免 JSON 重序列化造成歧义。

授权字段包含 `version`、`product`、`license_id`、`subject`、`device_id`、`issued_at` 与 `expires_at`。时间为 UTC Unix 秒；`issued_at <= 当前时间 < expires_at` 时才可通过，授权最长 366 天。令牌上限 4096 字节、payload 上限 2048 字节。`version` 固定为 `1`，`product` 固定为 `card-demo`；未知字段、重复字段及错误 JSON 类型均应被拒绝。

Windows 设备绑定为 `SHA-256("card-demo/device/v1\0" || lowercase(trim(MachineGuid)))`，从 64 位注册表视图读取 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`；读取或格式检查失败时拒绝校验。该算法保持既有 Windows 卡密的指纹兼容。

macOS 设备绑定为 `SHA-256("card-demo/device/macos/v1\0" || lowercase(trim(IOPlatformUUID)))`，使用独立的平台域，避免相同原始 UUID 在 Windows 与 macOS 上产生相同机器码。Rust 固定调用 `/usr/sbin/ioreg -r -d 1 -c IOPlatformExpertDevice -w 0`，清空继承环境，直接读取系统 I/O Registry；不经过 shell、PATH 查找或外部设备参数。探测限制为 3 秒和 64 KiB 标准输出；只接受唯一、格式有效且非全零的 `IOPlatformUUID`，读取失败、输出超限、超时、重复或缺失时均拒绝校验。[Apple ioreg 手册](https://github.com/apple-oss-distributions/IOKitTools/blob/main/ioreg.tproj/ioreg.8)、[Apple IOPlatformUUID 常量说明](https://developer.apple.com/documentation/iokit/kioplatformuuidkey)

两种平台的原始系统标识都不进入卡密。哈希结果仍然是可关联的设备标识，不等同于匿名数据、硬件防伪或硬件证明；管理员、被修改的系统或克隆环境可能仿冒标识。设备重装、更换或系统标识损坏都可能导致旧卡密无法使用，应准备人工重新绑定流程。

Qt 将 Rust 校验库静态链接到 `CardGuard` 主程序，在工作线程中通过 C ABI `cardguard_request` 传入自有 JSON 缓冲区；GUI 不启动外部 `license-client`，也不把可替换程序返回的 JSON 当作验签结果。主程序的 `--stdio` 入口直接使用同一个 Rust 有界协议循环，且不创建 QApplication；它只输出诊断结果，不授予 GUI 授权。独立 `license-client --stdio` 保留为可选工具，不属于 GUI 的运行依赖。Rust 自行读取设备标识、系统时间与编译公钥，请求不能注入这些值。

FFI 请求限制为 16 KiB、输出缓冲区为 64 KiB；调用者保证缓冲区存活、不重叠且不存在冲突访问，Rust 校验指针空值、长度、地址范围及输出容量后才读写。返回 0、异常、无效 JSON 或 `ok:false` 都不能授予授权。Qt 在 GUI 线程中再次检查结果字段、产品、版本、设备和时间。静态链接移除了外部 helper 的替换入口，但不能阻止管理员修改主程序或进程内存。

后台调用通过 `QtConcurrent` 和 `QFutureWatcher` 完成，worker 只持有自己的缓冲区与任务占用凭据，不持有窗口或控件指针。8 秒超时会撤销该次结果；进程内调用不会被强制杀线程，界面保持任务占用直到其实际结束，并忽略迟到结果，避免反复点击积累后台任务。窗口销毁会断开结果回调；本机设备探测自身仍有上述 3 秒限制。Release 使用 `panic=abort`，Rust 内部 panic 会终止进程，不能据此继续授予授权。

界面在校验成功后同时使用系统时间和单调计时器检查该次会话的剩余有效期；回拨到签发前或耗尽原有剩余时长都会撤销成功状态。该措施只能避免当前会话被简单回拨延长，重启后的可信时间问题仍未解决。

## 开源代码保护的范围

默认构建使用 [xollvm v0.11.1](https://github.com/und3ath/xollvm/releases/tag/v0.11.1) / LLVM 22，仅虚拟化 `frontend/authorization_policy.cpp` 中的 `cardguard_policy_allows`。它检查 Rust 成功、版本、产品、设备及字段检查对应的五个状态位均成立（`checks == 31`），并检查签发时间、到期时间、时间上界和最长 366 天期限。GUI 保留原有严格校验，最终接受授权前还必须通过这个策略函数。函数不持有私钥，也不替代 Ed25519 验签。

策略函数独立编译为 object 后链接进主程序；整个 Rust 校验器、Ed25519 实现、Qt DLL、framework 和插件都不参与这次虚拟化。当前注解关闭 anti-debug 相关选项，不依靠调试器探测或限制 Qt 库替换来建立信任。`build-policy.py` 检查 O2 优化后的 IR 中仍存在 `vm.bytecode` 和 `__vm_engine`，Windows 还检查 CFG 元数据，再用同一份 IR 生成 object。构建流程运行链接同一 object 的 `policy-tests`，包含 4174 个边界、状态组合与差分用例；是否实际通过以构建输出和 [验证记录](VALIDATION.md) 为准。

`protection.json` 记录源码、object、优化后 IR 与工具报告的摘要，以及版本、目标和保护范围，用于发现错用目标或陈旧构建。它是构建记录，摘要与文件一起被替换时无法建立可信性，不是运行时防篡改或签名信任链。

xollvm 的作用是增加所选函数的分析与修改成本。公开源码允许任何人移除策略门或保护注解后重新构建；获得程序控制权的人也可能直接修改结果分支。它不提供可信时间、远程鉴权、撤销能力或不可破解保证，UPX 压缩也不能补上这些边界。具体构建方式见 [PACKING.md](PACKING.md)。

## 演示私钥文件

`demo/keys` 保留加密格式便于重现签发流程，但配套口令已经公开，以下算法参数不代表这套测试身份仍具有保密性。正式身份应另行生成并保护口令。

发卡端生成 32 字节随机 Ed25519 seed，使用 Argon2id v19 派生 32 字节加密密钥，固定参数为 65536 KiB 内存、3 次迭代、并行度 1；每个文件使用新的 16 字节随机盐。随后用 ChaCha20-Poly1305、12 字节随机 nonce 和固定协议 AAD 加密 seed，JSON 文件只保存算法标识、固定参数、盐、nonce 和密文。

解密前检查文件上限 16 KiB、字段类型、参数和编码长度，避免把可修改文件中的任意参数直接交给 KDF。创建密钥文件采用排他创建，不覆盖已有文件。口令至少 12 个字符、最多 1024 个 UTF-8 字节，不允许控制字符；长度检查不能保证口令熵，应使用密码管理器生成的独立随机口令，并保护管理端目录的访问权限和备份。

默认从终端隐藏输入口令；`--passphrase-stdin` 只供受控自动化使用。正式或其他私有身份的明文口令不得放进命令行、PowerShell 历史、脚本或 Git；`demo/keys/demo.passphrase.txt` 是明确公开的测试数据例外。程序对持有的敏感缓冲区尽力清零，仍不能保证操作系统换页、崩溃转储、复制、调试器或恶意软件中从未出现过可恢复副本。

### Windows 开发便利模式

`scripts/init-demo.ps1` 自动生成随机口令，并将口令经当前 Windows 用户的 DPAPI 保护后保存到 `.local/demo-passphrase.dpapi`；私钥仍保存为上述 Argon2id + AEAD 加密文件。`.local` 设置独立 DACL，仅向当前用户、SYSTEM 和 Administrators 授权。`scripts/issue-demo.ps1` 在同一用户上下文解密口令，再经匿名管道交给发卡工具。

该模式仍在本机保存和使用 DPAPI 文件，不会因公开 demo 材料而上传或覆盖 `.local`。同一 Windows 用户下运行的程序仍可能解密 DPAPI 文件；它不提供独立第二因素，也不防御该账户被控制。如果对应签发身份已经在 `demo/keys` 公开，DPAPI 也无法恢复该身份的保密性。PowerShell/.NET 处理时会产生无法可靠清零的普通字符串。迁移电脑、丢失用户配置或 DPAPI 材料可能使其他本机私有身份的口令无法恢复，须保留受保护的恢复方案。正式签名服务应使用新建的独立身份、单独管理环境、人工输入的强口令或 HSM/KMS。[Microsoft PowerShell DPAPI 说明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/convertto-securestring?view=powershell-7.3)

初始化遇到“部分身份已存在”时会拒绝覆盖。中断可能留下公钥、加密私钥或 DPAPI 文件中的一部分，应先核实与备份这些文件，再决定如何重建演示身份；不得静默生成新密钥继续向已信任旧公钥的客户端发卡。

## 离线模式的固有限制

| 场景 | Demo 的边界 | 正式系统的应对方向 |
| --- | --- | --- |
| 系统时间被回拨 | 使用本机时间的到期校验无法建立可信时间 | 服务器签发短期租约；结合服务器时间、合理离线宽限与重放防护 |
| 可执行文件被修改 | 静态链接减少外部 helper 替换入口，主程序的验签、策略门或结果分支仍可被补丁修改 | 由服务端执行有价值操作并独立鉴权；代码签名和完整性验证作为补充 |
| 机器码被仿冒 | 本机标识不是不可伪造的硬件证明；克隆或修改系统可能复制标识 | 设备注册、设备私钥、风险控制；有需求时评估 TPM 与远程证明 |
| 授权转卖或共享 | 无设备绑定的卡密能被复制；设备绑定不能阻止客户端补丁 | 在线激活、并发限制、审计与可撤销的短期租约 |
| 紧急撤销、退款或密钥泄露 | 完全离线的旧客户端无法及时获知撤销状态 | 服务端撤销状态、签名密钥轮换和强制更新策略 |
| 卡密内容泄露 | 签名没有保密能力 | 减少明文信息；服务端保管敏感数据 |
| 本机管理员或恶意程序 | 可读进程内存、替换程序、截取口令和调用结果 | 隔离管理端、最小权限与受控发布；不能宣称客户端彻底防御本机管理员 |

本地“上次校验时间”、校验和、机器码哈希和加壳都不能把攻击者控制的电脑变成可信服务器。日志也不能作为离线不可回滚的可信存储。

## 面向生产的改进顺序

1. 建立独立授权服务：身份与订单记录、一次性激活码、设备注册、吊销、限流、短期租约和审计。应用每次进行有价值的服务器操作时，服务器重新鉴权。
2. 将正式私钥放入专用签名服务或合适的 HSM/KMS，限制调用身份、权限和频率；实行备份、双人审批、轮换和泄露响应。客户端只获得验签材料。
3. 使用操作系统信任链的代码签名、签名更新包与可信更新通道。代码签名证明发布者与文件完整性，不能替代授权校验，也不保证文件永远不被篡改。
4. 为威胁模型、协议、依赖与构建流程进行独立安全评审；使用锁定依赖、漏洞检查、最小权限 CI 和可追溯的发布制品。定期复审检查结果，而非承诺一次构建永久安全。
5. 对当前 xollvm 保护范围、性能和目标平台兼容性持续回归。逆向成本只能作为纵深防御的一层，不能成为私钥隔离、在线撤销或可信时间的替代方案。保护范围见 [PACKING.md](PACKING.md)。

## 处理疑似泄露

`demo/keys` 身份已经按设计公开，不应再把它视为只有项目所有者才能签卡的秘密。如果正式系统误用了该身份，应更换私钥并重建信任新公钥的客户端。其他私有身份疑似泄露时，同样不能仅修改私钥文件名或重新加壳。正式系统还应停止签发、撤销受影响租约、轮换服务端信任、发布更新并调查记录；完全离线的旧客户端仍可能信任旧密钥。
